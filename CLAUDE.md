# gestion_multipyme — Contexto para Claude Code

ERP multi-tenant en PHP/MySQL/AdminLTE para pymes argentinas, desarrollado por Developsam SAS.
Este documento existe para que Claude Code entienda la arquitectura ANTES de generar o modificar código.
No es un manual de usuario: es la guía de convenciones que el código no explica por sí solo.

## Stack

- PHP puro (sin framework) + MySQL/MariaDB (mysqli, prepared statements)
- AdminLTE + Bootstrap 5 + DataTables + SweetAlert2
- AJAX (jQuery) para toda interacción con backend, sin recargas de página
- Sin ORM: todas las queries son SQL directo en los archivos `_model.php`

## Arquitectura jerárquica

```
Empresas ──< Empresas_Modulos >── Módulos ──< Páginas (árbol vía padre_id) ──< Páginas_Funciones (botones/acciones)
Usuarios ──< Usuarios_Perfiles >── Perfiles ──< Perfiles_Funciones (qué función de qué página puede ejecutar)
                                            └─< Empresas_Perfiles ──< Empresas_Perfiles_Funciones (override por empresa)
```

- **Empresa**: cada empresa/cliente del sistema (multi-tenant). Casi toda tabla de negocio tiene `empresa_id`. Empresas actuales: 1 = CONFIGURACION, 2 = Casa Lucho (titular), 3 = CEC Patagones; solo en la base local, 6 = Developsam SAS (demo del módulo 5 `gestion_normal`, configuración clonada de la 2, usuarios jgili / gblanco). En `gestion` y `gestion_normal` ya no hay fallbacks a la empresa 2: ver `core/empresa_config.php`.
- **Módulo**: agrupación de páginas. `conf__modulos.modulo_id`; la carpeta sale de `modulo_url` y el prefijo de tablas de `base_datos`:

- **Página**: una pantalla del sistema. Vive en `conf__paginas`, con árbol vía `padre_id` y orden vía `orden`.
- **Función**: una acción posible dentro de una página (Agregar, Editar, Inhabilitar, Confirmar, etc.), vive en `conf__paginas_funciones`.
- **Perfil**: rol de acceso. Un usuario tiene un perfil por empresa (`conf__usuarios_perfiles`); el perfil determina qué funciones de qué páginas puede ejecutar (`conf__perfiles_funciones`, con posible override específico en `conf__empresas_perfiles_funciones`).

## El motor de estados (lo más importante de todo)

Cada tabla de negocio tiene una columna `tabla_estado_registro_id` (NO `estado_id` directo). **Pese al nombre, guarda el id GENÉRICO de `conf__estados_registros.estado_registro_id`** (1 Activo, 2 Inactivo, 3 Borrador, 4 Pend. Aprobación, 5 Confirmado, 6 Eliminado, 12 Facturado, 13 Pend. Facturación, 15 Fact. Parcial, 38 Anulado, etc.), no la PK de `conf__tablas_estados_registros`. Es lo que muestran los datos y la decisión 2 de `_local/docs/matriz-legal/03-plan-de-modulos.md`.

`conf__tablas_estados_registros` es el catálogo por tabla: para cada `(tabla_id, estado_registro_id)` da la etiqueta propia de esa tabla (`tabla_estado_registro`, p. ej. "Pendiente de ARCA" para el 4 en ventas_facturas), `orden`, `color_id`, `es_inicial` y `es_final`. El estado inicial de una tabla de proceso se resuelve con `es_inicial = 1` (patrón `vfEstadoInicial()` en `ventas_facturas_model.php` / `obtenerEstadoInicialCobranza()`), y para mostrar el nombre se hace `JOIN conf__estados_registros er ON er.estado_registro_id = x.tabla_estado_registro_id` (o se cruza `ter.tabla_id = N AND ter.estado_registro_id = x.tabla_estado_registro_id` para la etiqueta propia).

Tesorería se migró al id genérico el 2026-10-07 (`_local/sql/mantenimiento/20261007_tesoreria_04_estados_genericos.sql`; reemplaza lo que dice la spec v3.11 en §1/§381). Los ids genéricos 25 y 28–40 los usa el código como constantes fijas: ese script verifica que existan con esos ids. Estados derivados del saldo en `gestion__comprobantes`: 39 Cancelado parcial / 40 Cancelado total, asignados solo por `recalcularEstadoDestino()` sobre comprobantes en 5/39/40 (los cancelables son `CONFIRMADO` o `CANC_PARCIAL`); `syncComprobante()` no los revierte. El registro de origen acompaña ese cambio (`tesoreriaSincronizarEstadoOrigen()`) solo si el estado figura en `conf__tablas_estados_registros` de su tabla (hoy: ventas_facturas; para sumar otra tabla, cargar 39/40 en su catálogo y sus funciones/permisos desde esos estados, como `20261007_tesoreria_05_estado_origen.sql`). Asientos anulados = 2.

⚠️ Excepciones vigentes, no copiar: Matriz Legal (`modules/ml/`) guarda la PK de `conf__tablas_estados_registros` (2001–2200) y la cruza por PK, al revés de la decisión 2 de su propio plan. (`estudio_contable` usaba ids ordinales; desde `20261015_estudio_estados_01_genericos.sql` usa los genéricos con su significado: vencimientos 17/18/5/28/35/38, tareas 17/18/19/21/26, licencias 18/21, normas derogada 20, cliente suspendido 16.)

**Los botones de acción NO están hardcodeados.** Se calculan así:
1. `conf__paginas_funciones` define, para cada página, qué funciones existen y su transición: `tabla_estado_registro_origen_id → tabla_estado_registro_destino_id` (también ids genéricos; `origen = 0` = función de creación, la que devuelve `obtener_boton_agregar`).
2. Dado el estado actual de un registro, el backend filtra las funciones cuyo `origen_id` coincide **y que el perfil del usuario tiene asignadas** (`conf__empresas_perfiles_funciones`), y esas son las que se muestran como botones. El filtro por perfil es `permisos_filtrar_funciones($conexion, $funciones)` de `core/permisos.php` (filas con `pagina_funcion_id` y `pagina_id`; contexto = usuario / empresa que fijó `ajax_guard`, o la sesión); todo `obtenerBotonesPorEstado` / `obtenerBotonAgregar` y armadores propios (`vfBotonesPorEstado`, `monBotones`, `bco_botones`, `obl_botones`...) lo aplican desde el 2026-11-05, y `obtenerBotonAgregar` devuelve `null` si el perfil no tiene la función de creación (`permisos_sin_funcion_creacion`; el JS no muestra el botón). Un botón armado a mano (Cobranzas, Pagos, Cheques, Movimientos, Rendiciones) usa `permisos_puede($conexion, $pagina_id, 'accion_js')`, y la acción del `_ajax.php` lo exige también. En páginas sin motor de estados (todo Estudio Contable) el botón lleva `data-funcion="accion_js"` (en el HTML o en el JS que arma la fila) y `header1.php` oculta con CSS los que el perfil no tiene en esa página (`permisos_css_funciones_ocultas`); el `_ajax.php` llama, después de leer la acción, a `permisos_exigir_accion($conn, $pagina, $accion, ['accion del request' => 'accion_js'])` (403 JSON). Estudio usa las funciones de página ver / agregar / editar / inhabilitar: alta y procesos = agregar, modificar y cambiar estado = editar, baja / anular / revertir = inhabilitar (Mini-gestión: todo con su `agregar` 3449). Una transición automática del sistema (no un botón, p. ej. `resolverAccionTransicion`) lee `obtenerFuncionesPagina` sin filtrar. **En el servidor** (2026-11-05), todo `case 'ejecutar_accion*'` de `gestion*/` llama a `permisos_exigir_funcion($conexion, $pagina, $accion_js)` antes de la transición, y `agregar` / `editar` a `permisos_exigir_funcion(..., 'agregar', true)` (con `true` solo se exige si la página tiene esa función); un `_ajax.php` nuevo hace lo mismo. Los que reciben la página del request la pasan por `permisos_pagina_modulo($conn, $modulo, $pagina, 'url.php')`: solo vale una página del módulo del archivo; si no, la de esa url (antes, sin `pagina_idx`, Gestión Normal tomaba la del módulo 2). Las páginas de administración con botones fijos (Accesos por perfil, Autorizaciones de copia, Vinculaciones, Parámetros, Roles de cuentas, Categorías, Listas de precios por producto) usan `data-funcion` + `permisos_exigir_accion`, como Estudio.
3. El frontend ejecuta la acción vía `accion_js` (string como `'agregar'`, `'editar'`, `'inhabilitar'`, `'confirmar'`) contra el endpoint genérico `ejecutar_accion` del `_ajax.php`.

Dos "tipos de tabla" (`conf__tablas_tipos`) marcan la complejidad esperada:
- **Diccionario** (tipo 1): CRUD simple, solo Activo/Inactivo. Ejemplo: `depositos`.
- **Proceso Corto/Largo** (tipo 2/3): workflow con Borrador → Pendiente de Aprobación → Confirmado → Eliminado (y variantes: Pendiente de Recepción → Recibido, etc). Ejemplo: `facturas_proveedores`, `ventas_facturas`, `ordenes_compra`.

**Tipo de operación de la empresa** (2026-10-15, scripts `20261015_tipo_operacion_0{1,2,3}_*.sql`): `conf__empresas.tipo_operacion` BIENES / SERVICIOS / MIXTA (local: 2 BIENES; 3, 6, 7 SERVICIOS). Las páginas que solo sirven para vender bienes (pedidos, remitos, stock, depósitos, bocas, costos, marcas/modelos) tienen `conf__paginas.requiere_bienes = 1`; las OC y los presupuestos no (una empresa de servicios usa OC con recepciones parciales). Los perfiles base de Gestión (201–208 / 501–508: Administrador, Ventas, Compras y pagos, Tesorería, Contable e impositivo, Depósito y stock [BIENES], Facturación y cobranzas [SERVICIOS], Consulta) llevan `conf__perfiles.tipo_operacion` TODAS / BIENES / SERVICIOS, y al copiarlos a una empresa SERVICIOS se omiten las funciones de páginas `requiere_bienes`: todo en `core/perfiles_predefinidos.php`, que usan el asistente de inicio (paso 0) y `conf/empresas_modulos_model.php`. **Solo oculta** (el menú se arma con las páginas con funciones), no bloquea el acceso. Una página nueva de bienes se marca `requiere_bienes = 1` en su script; una página nueva que deba estar en los perfiles predefinidos se agrega a `conf__perfiles_funciones` de los perfiles base que correspondan.

Al crear una página nueva: primero definir su fila en `conf__tablas` (con el `tabla_tipo_id` correcto), después sus estados en `conf__tablas_estados_registros`, después sus funciones en `conf__paginas_funciones`, y por último los permisos en `conf__perfiles_funciones` **y** `conf__empresas_perfiles_funciones` (esta última es la única fuente que lee `core/permisos.php`; una página sin filas ahí queda denegada para todos salvo el superadmin `USUARIOS_ACCESO_TOTAL = [1]`). Sin esto, el motor de botones no tiene nada que mostrar. Todo alta de este tipo va en un script versionado en `_local/sql/mantenimiento/AAAAMMDD_<tema>_NN_<paso>.sql`, no en scripts sueltos de `_local/scratch/`.

## Estructura de archivos por página

Cada pantalla tiene 4 archivos, todos con el mismo nombre base:

| Archivo | Rol |
|---|---|
| `pagina.php` | Vista HTML. Incluye `header1.php`/`footer1.php`. Define `$modudo_idx` (⚠️ typo intencional y consistente en todo el proyecto — NO corregir a `$modulo_idx`) y `$pagina_idx` con el id de `conf__paginas`. |
| `pagina_ajax.php` (o `pagina-ajax.php`, hay ambas convenciones en el código viejo — para código nuevo usar `pagina_ajax.php`) | Dispatcher por `$_GET['accion']` / `$_POST['accion']`. Siempre responde `Content-Type: application/json`. |
| `pagina_model.php` | Toda la lógica de negocio y SQL. Funciones con `mysqli_prepare` + bind + `mysqli_stmt_execute`. Escrituras dentro de `mysqli_begin_transaction` / `commit` / `rollback` con try/catch. |
| `pagina.js` | jQuery + DataTables + SweetAlert2. Sin frameworks de componentes. |

### Estilo visual "ui-simple" (gestion y gestion_normal, desde el 2026-10-26)
Todas las páginas del menú de los módulos 2 y 5 lo usan; una página nueva también. Desde el 2026-11-05 también las de conf (módulo 1): fijan `$pagina_idx` (antes no, así que `header1.php` no controlaba el acceso a la vista), secciones "Empresas y accesos" / "Estructura del sistema" / "Otros" (nombres del menú en `20261105_conf_paginas_nombres_01.sql`) y su Inicio (`conf/index.php` + `inicio_model.php`: indicadores y "Para revisar": perfiles sin funciones, usuarios sin perfil, empresas sin módulos, páginas sin funciones / sin perfiles / sin archivo). La página pone `$ui_simple = true;` antes de incluir `header1.php` (agrega `body.ui-simple`) y arma el encabezado con `ui_encabezado($titulo, $icono, $ayuda, ['Sección del menú'], $acciones_html)` de `core/ui.php`: migas "Inicio / Sección / Página" (la sección es un desplegable con las páginas de esa carpeta del menú que el usuario puede ver: `header1.php` las deja en `$GLOBALS['ui_menu_secciones']` y `ui_miga_seccion()` toma la carpeta que contiene a la página actual), título corto, la descripción en un "?" y, a la derecha, el botón principal o los filtros globales. Estilos en `assets/css/ui-simple.css` (todo bajo `body.ui-simple`, salvo la corrección de etiquetas de estado `.badge.table-*`, que vale en todo el sistema) y comportamientos en `assets/js/ui-simple.js` (global `UiSimple`, no `UI`: varios archivos ya usan una constante local `UI = window.ComprobantesUI`). Reglas:
- Textos de ayuda: nunca fijos en pantalla; van en `ui_ayuda('…')` (un "?" con tooltip) junto al título o la etiqueta del campo.
- Tablas DataTables: **todas son responsive** (todos los módulos): `header1.php` carga Responsive 2.5.0 y pone `responsive: true` en los defaults; no cargarlo de nuevo en la página ni volver a cargar `jquery.dataTables` (pisa la extensión). Un handler `preInit.dt` de `header1.php` marca la columna de acciones (encabezado "Acciones" / "Acción" / "Opciones", o la última sin título) con `all` (nunca se oculta) y las `className: 'ui-detalle'` con `none` (datos secundarios: siempre en el detalle desplegable ▸ de la fila); una `ui-detalle` con encabezado "ID" / "#" se oculta del todo (no va al detalle: un ▸ que despliega solo el ID no sirve). Las acciones de la fila se ven todas, sin menú "⋮" (`ui-simple.js` solo les da el estilo liviano; `data-ui-acciones="no"` en la tabla lo desactiva). Ancho: `ui-simple.js` (todas las páginas) recalcula columnas y Responsive al mostrar una solapa / modal / collapse y cuando cambia el ancho del contenedor de la tabla (`ResizeObserver`), así que una tabla dentro de una solapa oculta no necesita `columns.adjust()` propio; si la página pone `max-width: 0` en las celdas (truco de elipsis), la tabla va con `autoWidth: false` y anchos en el `<th>` (ver las solapas de `productos.php`), porque DataTables mide mal esas columnas. El buscador va a la barra de la card (`.card-header.ui-barra` o la que tiene `#contenedor-boton-agregar`).
- Formularios: secciones con `.ui-seccion` / `.ui-seccion-titulo`, opcionales o avanzados en `<details class="ui-mas-opciones">`, obligatorios con `.ui-requerido` en la etiqueta, un solo botón principal.
- Filtros: contenedor `.ui-filtros` (anchos `.ui-f-fecha` / `.ui-f-media` / `.ui-f-ancha`); en celular se pliegan bajo un botón "Filtros".
- Indicadores: `.ui-kpi` (`.ui-kpi-etiqueta`, `.ui-kpi-valor`, `.ui-kpi-sub`), como mucho 3 o 4 por pantalla; solapas con `.ui-solapas`.
- Mensajes: `UiSimple.ok('Guardado')`, `UiSimple.aviso('Elegí un cliente.')`, `UiSimple.error(msg, 'No se pudo guardar')`: cortos y en lenguaje cotidiano. Además `ui-simple.js` intercepta `Swal.fire` en estas páginas: títulos genéricos ("Error", "¡Éxito!", "Atención") pasan a "No se pudo completar" / "Listo" / "Revisá los datos", los errores de conexión a una frase clara y los éxitos sin confirmación a un aviso que se cierra solo (su promesa responde `isConfirmed: true`, como si se hubiera aceptado). Las confirmaciones con Cancelar y los textos que vienen del servidor no cambian.
- Marco común (todos los módulos, en `header1.php`): empresa y módulo en un solo menú "Empresa · Módulo" (`.ui-contexto`); accesos directos grises, solo en pantallas grandes; el menú lateral muestra los nombres de `conf__paginas` sin el prefijo "Gestion - ". `header1.php` carga también `buttons.print.min.js` de DataTables (los botones `extend: 'print'` fallaban en las páginas que no lo incluían).

### Acciones estándar que todo `_ajax.php` implementa
`listar`, `obtener_boton_agregar`, `ejecutar_accion` (transición de estado genérica), `agregar`, `editar`, `obtener`, `obtener_estados` — más acciones específicas del dominio de esa página.

### Convención de respuesta
Todo devuelve JSON. Dos formatos conviven en el código actual:
- `{resultado: bool, ...}` — típico en `agregar`/`editar` (`_model.php` con `agregarX`/`editarX`)
- `{success: bool, error/message: string, ...}` — típico en acciones de estado y errores

Para código nuevo, preferir `{success: bool, data: ..., message: string}` de forma consistente (es el estándar que se está migrando en el resto del ERP).

### Seguridad del `_ajax.php` (obligatorio)
Todo `_ajax.php` arranca con el guard central `core/ajax_guard.php`, como primera instrucción (después de `declare(strict_types=1)` si lo hay):
```php
require_once __DIR__ . '/../../core/ajax_guard.php';
$ctx = ajax_guard(['pagina_idx' => 402]);   // $ctx['usuario_id'], $ctx['empresa_id']
```
- Exige sesión de `login.php` (si no, 401 JSON; `footer1.php` redirige al login en los 401 de jQuery).
- Resuelve la empresa de `empresa_idx` (u otros parámetros con `'params'`), si no viene de `$_SESSION['empresa_id']`, **sin default**, y valida que el usuario tenga perfil en ella (403). Si el parámetro no vino, lo completa en `$_GET/$_POST/$_REQUEST`, así el viejo `$_GET['empresa_idx'] ?? 2` toma la empresa de la sesión.
- Opciones: `'pagina_idx'` (acceso a esa página), `'modulo_id' + 'paginas_url'` (acceso a alguna de las páginas con esas urls; si ninguna está configurada, solo superadmin), `'empresa' => false`, `'solo_superadmin' => true`.
- Usar `$ctx['empresa_id']` / `$ctx['usuario_id']`; nunca `$_SESSION['usuario_id'] ?? 1` ni empresa por default.
- CSRF: `core/csrf.php` (`csrf_token()` en la página, `csrf_exigir()` en la acción; header `X-CSRF-Token`). Por ahora solo lo usan las acciones `lectura_*` de `gestion_normal/facturas_proveedores_ajax.php`; el resto de los `_ajax.php` no valida CSRF.
- `$pagina_idx` fijo en el archivo, nunca del request. Si una página no puede fijarlo, usar `pagina_id_por_url()` de `core/permisos.php` (ver `gestion/clientes.php`).
- Estado actual: todos los `_ajax.php` de `gestion/` y `conf/` validan sesión + empresa + página (también los del 2026-10-14: `empresa_inicio`, `empresas_autorizaciones_copia`, `empresas_vinculaciones`, que pasan `'params' => ['empresa_id', 'empresa_idx']` porque su JS manda `empresa_id`). Los que se usan desde varias pantallas listan todas en `paginas_url` (p. ej. `ventas_remitos_ajax.php` → pedidos, nuevos pedidos, remitos y pendientes de facturación): **si una pantalla empieza a llamar a un endpoint de otra, agregarla a ese `paginas_url`**, si no sus usuarios reciben 403. `ml/` y parte de `estudio_contable/` validan página con su propio código.
- Las páginas legacy fuera del menú que quedan (`depositos.php`, `pedidos_clientes.php`, `impuestos_jurisdicciones.php`, `funciones_contexto.php` de `gestion/`) no fijan `$pagina_idx`, así que `header1.php` las abre para cualquier usuario logueado; sus endpoints, al no tener página configurada, quedaron solo para superadmin.

En el XAMPP local `php.ini` tiene `session.auto_start=1`, así que `$_SESSION` existe aunque el archivo no llame `session_start()`; no asumir lo mismo en producción (el guard llama `session_start()`).

### Accesos por sucursal (`core/accesos_sucursales.php`)
Capa de autorización adicional a la de páginas: `AccesosSucursalesHelper` resuelve qué sucursales / bocas / puntos de venta / tipos de comprobante puede usar un usuario según `gestion__perfiles_sucursales` (por `empresa_perfil_id`; `sucursal_id NULL` = toda la empresa) más `gestion__usuarios_sucursales_excepciones` (`PERMITE` suma, `DENIEGA` gana siempre, con vigencia `fecha_desde/hasta`). Sin filas = sin acceso (salvo `USUARIOS_ACCESO_TOTAL`). Se administra en `gestion/accesos_perfiles.php` (página 441). Uso en modelos:
- Listados: `$sql .= AccesosSucursalesHelper::filtroSqlSucursal($conexion, $uid, $empresa_id, 'alias.sucursal_id')`.
- Combos: `filtrarSucursales()` / `filtrarBocas()` / `filtrarPuntosVenta()` (si no hay `usuario_id` en sesión devuelven la lista completa).
- Escrituras: `exigirAccesoSucursal()` / `exigirAccesoPuntoVenta()` (lanzan `RuntimeException`).
Ya está aplicado en ventas (pedidos, remitos, facturas), compras (OC, facturas de proveedores), stock_ajustes, sucursales_ubicaciones y cobranzas. El código lo incluye con `if (file_exists(...))`.

## Entorno de desarrollo

**Todo lo que no va a producción vive en `_local/`** (desde el 2026-10-18): `_local/sql/` (volcados y `mantenimiento/`), `_local/docs/`, `_local/scratch/`, `_local/tests/`, `_local/tools/`, `_local/perf/`, más salidas generadas en local (`_local/salidas_locales/`). Un script, diagnóstico o documento nuevo va en `_local/`; un PHP de `_local/` que incluye código de la app sube un nivel más (`__DIR__ . '/../../db.php'`).

No hay gestor de paquetes ni build step: sin `composer.json`, sin `package.json`, sin bundler. El proyecto se sirve directo desde la raíz con Apache/XAMPP. No hay `npm test` ni `phpunit`. Ver `_local/tests/simulacion/README.md`; lo opera el agente `tester-circuitos`. El grupo `global_normal` (casos 20–25, `_local/docs/pruebas/prueba_global_gestion_normal.md`) da de alta dos empresas nuevas por las pantallas (conf, asistente de inicio, ABM) y corre 20 operaciones por empresa con retenciones sufridas; `global_gestion` corre los mismos casos sobre el módulo 2 (corrida aparte); lo que no tiene página lo registra como brecha (`brecha()`), no como falla.

Base de datos: `gestion_multipyme` en local (MariaDB 10.4.22); producción es `ps_gestion_casalucho` en otro servidor (MySQL 8.0.46). Todo script SQL tiene que correr en los dos motores: sin `ADD INDEX IF NOT EXISTS`, sin columnas `JSON`, sin `DEFAULT` en `TEXT`, charset `utf8mb4` / `utf8mb4_unicode_ci`, y el DDL no es transaccional (los scripts deben poder reanudarse). **Varios sistemas, un maestro** (2026-11-11): cada sistema es una carpeta completa de `htdocs` con su base (`casalucho` = maestro / `gestion_multipyme`, `ps_casalucho`, `estudio_gili`, `developsam`) y a producción se sube la carpeta tal cual. Se actualizan desde el gestor `htdocs/proyectos/` (fuera de este repo): botón **Código** (espejo de `casalucho` con vista previa; no pisa lo editado en el destino ni borra sus archivos propios; manifiesto `.proyectos_codigo.json` y respaldos en `<carpeta>/_local/respaldos_codigo/`) y botón **Base** (scripts de `_local/sql/mantenimiento/` con su estado en `conf__migraciones` de cada base, script `20261111_migraciones_registro_01.sql`: aplicar con `mysql.exe` en orden, anotar "ya aplicado" / "no corresponde", o descargar un paquete `.sql` para producción que anota cada script al terminarlo). Un script que no va a todas las bases (sincronizaciones entre bases, migraciones de un servidor, datos o perfiles de una empresa) lleva en su primera línea `-- @migracion: particular`; los demás se ofrecen a todas. Por eso los scripts se identifican por el nombre de archivo: no renombrar uno ya aplicado (se vería como nuevo) y, si se corrige uno ya aplicado, el gestor lo marca "cambió el script". Volcados de referencia en la raíz: `casalucho_local.sql` (el más actual), `casalucho_desarrollo.sql`, `casalucho_produccion.sql`. **Conviven varios puntos de conexión** porque el proyecto migró de convención más de una vez:

## Multi-tenant

Casi toda función de `_model.php` recibe `$empresa_idx` y lo usa en el `WHERE` de cada query. **Nunca omitir el filtro de empresa** — es el único aislamiento entre clientes del sistema. `header1.php` resuelve la empresa activa desde `$_GET['empresa_id']`, si no viene desde `$_SESSION['empresa_id']`, y si tampoco usa la empresa 2 o la primera disponible; la guarda en `$_SESSION['empresa_id']` / `$_SESSION['modulo_id']` y valida contra `conf__empresas_perfiles` + `conf__usuarios_perfiles` que el usuario tenga acceso. Después corta si el usuario no tiene permiso sobre `$pagina_idx` (solo si `$pagina_idx > 0`: una página que toma `$pagina_idx` de `$_GET`, como `clientes.php` y `proveedores.php`, queda sin control si se pasa `pagina_id=0`). El sidebar arma los links como `url?pagina_id=N&empresa_id=E&modulo_id=M`.

Excepción deliberada al aislamiento: `estudio_contable` (tenant del estudio = empresa 2) lee datos de otra empresa cuando `estudio__clientes.empresa_vinculada_id > 0` (modo "ERP" de mini-gestión y consola de auditoría); `estudio__vinculaciones` está pensada para registrar ese consentimiento, pero hoy el código no la consulta. Desde el 2026-10-14 existe además el consentimiento general `conf__empresas_vinculaciones` (ver "Vinculaciones entre empresas"), que el estudio tampoco consulta todavía: `estudio_cliente_obtener_empresa_erp()` (acción `obtener_empresa_erp` de `estudio_clientes_ajax.php`) precarga datos de cualquier empresa sin verificar vínculo.

## Dominios transversales

### Comprobante universal
Todo documento con número (factura de venta, de proveedor, remito, pedido, recibo RCX, OP, etc.) tiene una fila espejo en `gestion__comprobantes`, ligada por `(tabla_origen_id = conf__tablas.tabla_id, registro_origen_id)` (UNIQUE). La crea/actualiza `syncComprobante($conexion, $data, $tabla_origen_id)` (hay dos copias con el mismo nombre: `ventas_facturas_model.php` y `facturas_proveedores_model.php`, no se pueden incluir juntas) o variantes propias (`syncComprobanteCobranza`). Lleva `importe_pendiente` (saldo, caché que mantiene tesorería) y `signo`. Numeración: `comprobante_nro = 0` en Borrador y se numera al confirmar; `uk_comp_numeracion` impide duplicados (la numeración de proveedores es por entidad, tabla 84). Va sobre la columna generada `comprobante_nro_unico`, NULL en número 0 y, desde `20261110_comprobantes_nro_unico_eliminados_01.sql`, también en estado 6 Eliminado (un comprobante eliminado libera su número).
Tipos de comprobante: `gestion__comprobantes_grupos` → `_subgrupos` (tienen `tabla_id`, `tipo_asiento_id`, `origen_asiento`) → `_tipos` (`comprobante_fiscal_id`, `letra`, `signo`, `impacta_stock/contabilidad/ctacte`). Los tipos que ofrece una página se resuelven `pagina → conf__paginas.tabla_id → subgrupos con ese tabla_id → tipos`, intersectado con `gestion__puntos_venta_comprobantes` del punto de venta (ver `vfTiposPorPuntoVenta`).

### Fiscal

- Receptor: `gestion__entidades_condiciones_fiscales` vigente a hoy; sin entidad = Consumidor Final (condición 2).
- `gestion__comprobantes_relacion_fiscal` (página 110): matriz emisor × receptor → `comprobante_fiscal_id` (A/B/C…) y `discrimina_iva`.
- IIBB: `gestion__iibb_regimenes`, `gestion__iibb_jurisdicciones_sedes`, `gestion__jurisdicciones`, `gestion__entidades_condiciones_iibb` (+ `_jurisdicciones`: altas de un CM), padrón de percepción en `gestion__padrones_iibb` (`gestion__entidades_impuestos_padron` quedó sin uso).
- **Percepciones IIBB practicadas** (empresa agente; diseño y normativa de Río Negro en `_local/docs/gestion/09_percepciones_iibb.md`): una fila de `gestion__empresas_impuestos_config` por empresa × jurisdicción × régimen (`impuesto_tipo_id = 6`, vigencia por `f_desde/f_hasta`, datos del agente en la solapa "Agente de Percepción" de la página 73) + alícuota por situación del cliente en `gestion__empresas_impuestos_config_situaciones`. Las fuentes de alícuota y los formatos de DDJJ van por driver (`percepciones_iibb_drivers.php`, docs §12): cada fuente (archivo, servicio web, carga manual) escribe filas normalizadas con vigencia y `situacion` en `gestion__padrones_iibb`, y el motor solo lee esas filas; sumar una provincia es sumar un driver, sin tocar el motor. ### Tesorería (páginas 100–109, tablas 270–289)

## Convenciones de código a respetar

- `mysqli` puro, siempre prepared statements con bind por tipo (`"iis"`, etc.), nunca concatenar variables en el SQL.
- Debug vía `error_log()` con prefijos tipo `"=== INICIO editarDeposito ID: $id ==="`, no `var_dump`.
- Nunca ids fijos de configuración de una empresa (tipo de asiento, moneda, cuentas contables, subgrupos/tipos de comprobante, boca, medio de pago, punto de venta, tipo de producto, alícuota de IVA): se resuelven por `empresa_id` + código con `core/empresa_config.php` (`emp_tipo_asiento_id`, `emp_moneda_id` / `emp_moneda_base_id`, `emp_cuenta_id` / `emp_cuenta_concepto_id`, `emp_subgrupo_id`, `emp_boca_id`, `emp_medio_pago_id`, `emp_cuit`...). Cada empresa tiene su propio plan de cuentas: las cuentas por defecto nunca se buscan por id ni por código del plan, salen del concepto de la empresa en `gestion__empresas_cuentas_conceptos` (Tesorería > Conceptos Contables: DEUDORES_VENTAS, VENTAS, IVA_DEBITO, PROVEEDORES, VALORES_CARTERA, IVA_A_PAGAR, GASTOS_GENERALES, MERCADERIAS, EMPLEADOS, VALORES_A_PAGAR; siembra `_local/sql/mantenimiento/20261010_cuentas_conceptos_01_siembra.sql`) y, si no está, de `gestion__cont_parametros`; si tampoco, error explícito. Todo asiento pasa por `emp_validar_cuentas_asiento()`: ninguna cuenta de otra empresa. El certificado de ARCA es de cada empresa: el CUIT de la integración tiene que ser el de `conf__empresas.documento_numero` y la página solo lista certificados emitidos para ese CUIT. Cada empresa tiene sus puntos de venta: en los comprobantes propios `comprobante_pv` guarda el **id** del PV, pero lo que se muestra es su `codigo_fiscal` (el de ARCA y la impresión): en PHP `emp_numero_comprobante()` / `emp_pv_numero()`, en SQL `emp_sql_pv_mostrar()` (en la tabla 84, facturas de proveedores, `comprobante_pv` es el PV del proveedor y se muestra tal cual). Nunca formatear `comprobante_pv` / `punto_venta_id` directo con `str_pad`/`padStart`. Todo catálogo por empresa (monedas, IVA, tipos de producto, categorías, condiciones de pago, listas, medios de pago) se consulta con `WHERE empresa_id`. En un `_ajax.php` la empresa es `$ctx['empresa_id']`, nunca un default `?? 2`.
- **Formato de fechas e importes en pantalla** (2026-10-31, script `20261031_formato_empresa_01_columnas.sql`): es de cada empresa, en `conf__empresas.formato_fecha` (`d/m/Y` por defecto, `m/d/Y`, `Y-m-d`, `d-m-Y`, `d.m.Y`) / `separador_miles` (PUNTO / COMA / ESPACIO / NINGUNO) / `separador_decimal` (COMA / PUNTO), editables en Empresas (página 27). Nunca formatear a mano (`toLocaleString('es-AR')`, `Intl.NumberFormat('es-AR')`, `split('-').reverse()`, `moment().format('DD/MM/YYYY')`, `number_format(x, 2, ',', '.')`, `date('d/m/Y')`): en JS `Fmt.fecha(v)` / `Fmt.fechaHora(v)` / `Fmt.numero(v, decimales u opciones de Intl)` / `Fmt.moneda(v)` / `Fmt.numberFormat(opciones)` / `Fmt.parseNumero(texto)` (`assets/js/formato.js`, lo carga `header1.php` con `window.APP_FORMATO`); en PHP `fmt_fecha()` / `fmt_fecha_hora()` / `fmt_numero()` / `fmt_moneda()` (`core/formato.php`; `header1.php` y `ajax_guard` activan la empresa; un modelo que los use hace `require_once` de `core/formato.php`). Cantidades de stock: `conf__empresas.decimales_stock` (0–4, default 2, script `20261107_formato_empresa_02_decimales_stock.sql`, editable en Empresas): en JS `Fmt.cantidad(v)` / `Fmt.cantidadInput(v)` (valor de un input number) / `Fmt.redondearCantidad(v)` / `Fmt.pasoStock()` (step), en PHP `fmt_cantidad()` / `fmt_redondear_cantidad()` (lo usa hoy Ajustes de Stock, que guarda las cantidades redondeadas). Los datos viajan siempre en ISO y con punto decimal: solo cambia lo que se muestra (inputs, CSV, claves y textos que se guardan, como la descripción del asiento, no se formatean). En todo DataTable, `formato.js` muestra con el formato de la empresa cualquier fecha ISO que llegue sin formatear a una celda (el dato sigue en ISO y ordena bien), ordena como fecha las columnas ya formateadas y fija los separadores de cada tabla en `preInit` (pisa el `decimal` del `es-ES.json`). Las impresiones (`templates/impresion/`, `*_print.php`) todavía no lo usan.
- Helpers de asset ya existentes: `asset_local()` (assets propios) y `asset()` (assets AdminLTE/vendor). `url()` para construir rutas internas.
- Los estados "obtener nombre de estado" hacen `SHOW COLUMNS` defensivo sobre `conf__estados_registros` antes de armar el SELECT (por si la columna se llama `estado_registro`, `nombre_estado` o `descripcion` según versión de la tabla). Mantener esa compatibilidad al tocar ese código, no asumir un solo nombre de columna.
- Librerías de terceros (DataTables y plugins, jszip, pdfmake, SweetAlert2, Select2, Font Awesome, Google Fonts…) **locales**, sin CDN: `assets/<css|js|fonts>/<librería>-<versión>/` (con la estructura relativa del paquete para sus `url()`), cargadas por `<script src>` / `<link>` en cada `pagina.php` con `asset_local()`; no hay bundler. En los `.js` se usa `window.APP_ASSETS_URL + 'js/…'` (lo define `header1.php`). Las páginas que no cargan `config.php` incluyen `core/assets.php` (`BASE_URL`, `asset()`, `asset_local()`, `url()`). Una librería nueva se descarga ahí con versión fija; nunca URLs de CDN ni versiones flotantes (`@11`). Única excepción: `exportar_productos_offline.php`, cuyo HTML se abre fuera del servidor.

Antes de generar una página nueva, replicar el patrón de 4 archivos + las 3 tablas de configuración (`conf__tablas`, `conf__tablas_estados_registros`, `conf__paginas_funciones`) usando `depositos` como plantilla si es CRUD simple, o `facturas_proveedores` si involucra workflow de estados y/o detalle. Ante cualquier duda sobre una convención no cubierta acá, preguntar antes de inventar un patrón nuevo.
